# Trezor Safe 7 support (USB and Bluetooth)

Adds support for the Trezor Safe 7 to Feather. Older Trezors are untouched.

This is long because the change is large and touches the device layer. The
summary is: the Safe 7 speaks a protocol Feather does not implement, so the
protocol had to be implemented; and it is the first Trezor with Bluetooth, so a
Bluetooth transport had to be written.

---

## 1. Why this is needed

Feather cannot talk to a Trezor Safe 7 at all. Not partially — the connection
fails before anything useful happens.

The Safe 7 (internal model `T3W1`) presents the same USB vendor and product id
as earlier Trezors, so Feather finds it, tries to speak to it, and gets nothing
back. The reason is that its firmware is built with the `thp` feature, which
replaces the legacy wire protocol with **Trezor-Host Protocol v2**.

That is not a negotiation. It is a compile-time either/or in the firmware: a
Safe 7 does not serve the legacy protocol at all, and no amount of retrying
reaches it. Supporting the device means implementing THP.

---

## 2. What THP is, and why it is a large change

The legacy protocol is framing. Messages are chunked into 64-byte packets with
a `##` marker and reassembled. There is no session, no key exchange, and no
authentication — the transport is assumed trustworthy.

THP v2 is a secure channel. Before any wallet message is exchanged:

1. **Channel allocation.** The host asks for a channel; the device answers with
   a channel id and its capabilities.
2. **Noise XX handshake** (`Noise_XX_25519_AESGCM_SHA256`) with a masked static
   key, producing per-direction encryption keys.
3. **Pairing**, the first time a given host and device meet. The device shows a
   six-digit code, the host echoes it back, and both sides run **CPace** over it
   to prove the same code was seen at each end.
4. **Credential exchange**, so later connections skip the pairing dialog.
5. **Session creation**, after which wallet messages flow encrypted.

Every one of those steps had to be implemented, along with the primitives they
need. That is where most of the work in this pull request went — not the
Bluetooth support, which is comparatively mechanical.

### 2.1 Primitives that were not available

Two pieces are not in OpenSSL or libsodium, and had to be implemented from the
specifications:

- **X25519 with an arbitrary base point.** Standard X25519 APIs multiply by the
  fixed generator. CPace requires multiplying by a point derived from the
  password, so the scalar multiplication had to be written directly against
  field arithmetic.
- **Elligator2** (RFC 9380), which maps a hash to a curve point. CPace uses it
  to turn the pairing code into the base point above.

The field arithmetic is the ref10 implementation already present in monero's
`crypto-ops.c`, extracted and placed in an anonymous namespace so it keeps
internal linkage and does not collide with the exported `fe_add`, `fe_invert`,
`fe_tobytes`, `load_3` and `load_4` symbols that cncrypto already provides.

### 2.2 Correctness

`thp_curve25519` and `thp_crypto` are covered by 30 unit tests, including
differential tests against reference vectors generated by
`contrib/thp/gen_vectors.py`. Those tests caught a real bug during development:
in AES-GCM the output length variable was being reused across the AAD and
ciphertext calls, silently skewing the ciphertext offset.

## 3. How the pieces fit together

```
device_trezor.cpp                wallet-level Monero operations, unchanged
device_trezor_base.cpp           device lifecycle, pairing UI plumbing
  transport.cpp                  chooses a transport, enumerates devices
    transport_ble.cpp            Bluetooth transport (THP only)
    transport_ble_win.cpp        Windows backend (WinRT)
    TrezorBleLinux.cpp           Linux backend (BlueZ), lives in Feather
    TrezorBleMac.mm              macOS backend (CoreBluetooth), lives in Feather
  protocol_thp.cpp               THP: channel, handshake, pairing, sessions
    thp_wire.cpp                 packet framing, CRC, alternating-bit protocol
    thp_crypto.cpp               Noise, HKDF, AES-GCM, CPace helpers
    thp_curve25519.cpp           X25519 with arbitrary base point, Elligator2
```

Which protocol to use is decided by probing the device on connect. `ProtocolV1`
is untouched, so **Trezor One, Model T, Safe 3 and Safe 5 continue to work
exactly as before**. Bluetooth pins THP without probing, because Bluetooth was
introduced alongside THP and the legacy protocol was never carried over it.

## 4. Bluetooth

### 4.1 Why the obvious Windows approach cannot work

The first implementation used the Win32 GATT API. It never found a device, and
could not have. That API enumerates device interfaces created by the operating
system's pairing flow, so it only ever sees peripherals Windows has already
bonded with. A Trezor advertising its GATT service is not one of those.

The device also does not appear in the Windows "Add a device" list, because a
peripheral advertising only a custom 128-bit service is not offered there. The
result looks exactly like a broken device rather than the wrong API.

Every working Trezor Bluetooth host takes the other route: scan raw
advertisements, filter by the service UUID, and connect without bonding.
`trezorlib` does this with `BleakScanner`; the Trezor Flutter client does it
with `universal_ble`. On Windows the only API that can do this is WinRT, so the
backend was rewritten against it.

### 4.2 What the Windows backend has to do that others do not

Reaching WinRT from a mingw-w64 cross build is possible but not free. Three
things are worth knowing, because each is a deliberate choice rather than an
accident:

- **Async calls are awaited by polling `IAsyncInfo`** rather than by installing
  completion handlers, so they behave identically in either COM apartment and
  need no message pump. The wallet calls this from several threads, and Qt puts
  the GUI thread in a single-threaded apartment.
- **Event handlers are hand-rolled COM objects that advertise `IAgileObject`**,
  so the runtime invokes them directly on a threadpool thread instead of
  marshalling back to the apartment that registered them. Without this, a
  handler registered from the GUI thread would only fire while a message pump
  runs, and the transport blocks without pumping.
- **Four interfaces are declared by hand** from the Windows SDK IDL, because
  mingw-w64 14 does not define them: `IBluetoothLEDevice3`,
  `IBluetoothLEDeviceStatics2`, `IDeviceInformationPairing`/`2` and friends, and
  `IBluetoothLEAdvertisementWatcher3`. Published COM interfaces are immutable,
  so transcribing them is safe, but the vtable order must match the IDL exactly.

One value could not be found in any header: the parameterised IID of
`ITypedEventHandler<DeviceInformationCustomPairing*, DevicePairingRequestedEventArgs*>`.
WinRT derives such IIDs deterministically, as a UUIDv5 over the generic type
signature, so it is computed offline by `contrib/trezor/piid.py`. That script
**validates its own derivation** by first reproducing a parameterised IID the
headers do publish, so the computed value is not taken on trust.

### 4.3 Behaviours that look like bugs and are not

These cost the most debugging time and are all documented in the code:

- **The device only advertises while in Bluetooth pairing mode.** Outside it,
  scanning finds nothing.
- **The advertised address is a resolvable private address and rotates.** A
  remembered address goes stale on its own schedule, so a failed connection
  rescans and retries rather than giving up.
- **Entering pairing mode mints a new device identity.** Any bond the operating
  system holds is then dead, and the link fails during encryption setup. On
  Windows the stale bond has to be removed explicitly or every later attempt
  fails identically.
- **Pairing must not be requested up front.** The Trezor Flutter client
  deliberately requests it only on Android, noting that elsewhere the platform
  arranges it and asking explicitly goes wrong. It goes wrong here too: an
  unsolicited pairing request makes the device leave pairing mode. The
  subscription is attempted first, and pairing is driven only if the device
  refuses for want of an authenticated link.
- **Writes must be acknowledged** (`WriteWithResponse`), matching the write
  characteristic's properties.
- **Packets are a fixed 244 bytes**, not derived from the negotiated MTU. The
  firmware packs to 244 regardless, and both ends must agree on one number.

### 4.4 Platform support

| Platform | Backend | State |
|---|---|---|
| Windows | WinRT | Working, tested against hardware |
| Linux | BlueZ over QtDBus | Written, compiles clean, **not tested against hardware** |
| macOS | CoreBluetooth | Written, **not compiled** — no toolchain was available |

USB is a separate matter and is in better shape. Nothing in the USB or protocol
path is platform-specific: the only place the operating system is consulted at
all is the pairing credential's location, and both branches are implemented. USB
support is therefore complete on every platform by construction — but it has
only been built and exercised on Windows, which is a weaker claim than "tested
everywhere" and is not being made here.

The Linux and macOS backends live in Feather rather than in monero, because
monero's device layer deliberately depends on no particular Bluetooth stack and
exposes `hw::trezor::ble::set_backend_factory()` for the host application to
supply one. Windows is the exception only because its backend needs nothing
outside the platform SDK.

**This should be weighed when reviewing.** Two of the three backends are
unverified against real hardware. They are structured identically to the tested
one and follow the same sequence, but that is an argument for plausibility, not
evidence.

## 5. New dependencies

**None on any platform.**

- Windows links `windowsapp`, `runtimeobject`, `ole32` and `uuid`, all of which
  ship with the platform SDK and are already available to the mingw-w64 cross
  build.
- Linux uses QtDBus. Feather already links Qt, and the backend is only built
  when `Qt6::DBus` is found, so a build without it simply has no Bluetooth
  rather than failing.
- macOS uses CoreBluetooth and Foundation, both part of the system.

No new third-party library is vendored, downloaded or linked. The protocol
implementation uses OpenSSL, which monero already depends on, for SHA-256,
SHA-512, HMAC and AES-GCM.

## 6. Security model

This section matters more than the rest, and reviewers should read it closely.

### 6.1 What THP changes

Under the legacy protocol the USB link is trusted implicitly. Under THP the
link is authenticated and encrypted, and the pairing code is what establishes
that. **This is a strict improvement**, and it is what makes Bluetooth
defensible at all: the security of the channel no longer rests on the transport
being trustworthy.

The pairing code is not a formality. Typing it back is what completes the CPace
exchange and rules out a man-in-the-middle. It cannot be confirmed on the device
alone the way a passphrase can, because the whole point is proving that the same
code was seen at both ends of the channel.

### 6.2 What is stored, and where

Pairing produces a credential, stored outside the wallet file because it belongs
to the (host, device) pair rather than to any wallet:

- Windows — `%APPDATA%\feather\trezor_thp_credentials.json`
- Linux/macOS — `$XDG_CONFIG_HOME/feather/trezor_thp_credentials.json`

**It contains no wallet keys and no spending authority.** It identifies this
host to this device so the pairing dialog can be skipped. Deleting the file
means pairing again, and nothing else. It is not encrypted, which is consistent
with what it is; an attacker who can read it has already got filesystem access
as the user.

### 6.3 What Bluetooth changes

Bluetooth widens the attack surface, and honestly so:

- The transport is now over the air rather than a cable. THP encrypts and
  authenticates the channel, so an eavesdropper sees ciphertext, but the device
  is now reachable by anything in radio range while it is advertising.
- The device only advertises in pairing mode, which bounds the exposure — but
  that is a property of the firmware, not something Feather enforces.
- Bluetooth bonding is handled by the operating system. Feather does not
  implement key exchange at the link layer and does not store link keys.
- **Feather removes a stale operating-system bond** when the device no longer
  honours it. This is necessary — the device changes identity on re-pairing —
  but it is a real capability, so it is deliberately narrow: it is only reached
  after a connection has already been established to that specific device and
  service discovery has come back unreachable. It never removes bonds for other
  devices and never runs speculatively.

### 6.4 A gap worth naming

The Bluetooth bonding ceremony is `ConfirmPinMatch`: the device displays a
six-digit code, and the user is meant to confirm it matches what the host shows.
**Feather currently auto-accepts and does not display that code.** The user
confirms on the device with nothing to compare against, which weakens that
particular check to "someone pressed the button".

This does not undermine the THP pairing above it — that code *is* shown and
typed, and it is what actually authenticates the channel — but it should be
fixed, and it is tracked. It is called out here rather than left for a reviewer
to find.

### 6.5 Attack surface added to the codebase

The protocol implementation parses attacker-influenced input: framed packets
with lengths and CRCs, and protobuf messages inside an encrypted channel.
Framing is length-checked and CRC-checked before use, packet sizes are fixed
and validated, and the unit tests include malformed input. The hand-declared COM
interfaces are a correctness risk rather than a memory-safety one — a wrong
vtable order would crash immediately, not silently corrupt.

## 7. Code style and conventions

- New Feather sources carry SPDX headers and follow the existing file layout.
  New monero sources carry the monero copyright header.
- Naming follows each side's local convention: `m_member` and `camelCase` in
  Feather, `snake_case` in monero's device layer.
- Comments explain **why**, not what. Where a line looks wrong but is
  deliberate — polling instead of handlers, a named namespace instead of an
  anonymous one, a fixed 244 instead of the MTU — the reason is written down,
  because every one of those was arrived at by getting it wrong first.
- No formatting-only changes to existing files, so the diff is reviewable.

## 8. Three bugs that failed silently

Worth stating because they shaped the code, and because each produced a
confident-looking success with nothing behind it:

1. **Interfaces in an anonymous namespace.** Hand-declared COM interfaces given
   internal linkage let the compiler conclude it can see every implementation.
   Finding none, it devirtualised the calls into something that crashed on the
   first invocation. They are in a named namespace for this reason.
2. **`Q_OBJECT` in an anonymous namespace.** moc generates nothing for such a
   class, with no diagnostic, and the notification slot is never connected — the
   device would connect and then hang forever.
3. **A platform `#if` around a Qt source file.** moc preprocesses without the
   compiler's platform macros, so a plain `__linux__` guard hid the class from
   it entirely. The guard tests `Q_MOC_RUN` as well.

All three were found by compiling and running rather than by reading.

## 9. Testing

- 30 unit tests over the protocol primitives and framing, including differential
  tests against generated reference vectors.
- `feather --test-ble` runs the production Bluetooth path headlessly and reports
  which stage failed. This exists because failures behind the wallet wizard are
  indistinguishable from "no device found", and it is what made the Bluetooth
  bugs findable.
- Verified end to end against a real Trezor Safe 7 on Windows: scanning,
  bonding, THP pairing, wallet creation, and transaction signing.
- Regression-checked against USB, which is unaffected.

## 10. Things to consider going forward

Named plainly rather than left to be discovered:

1. **Linux and macOS Bluetooth are unverified against hardware**, and macOS has
   never been compiled. They should be treated as untested code.
2. **The Bluetooth bonding code is not displayed** (§6.4).
3. **Reconnecting to a sleeping device.** Discovery is by advertisement only, so
   a bonded but idle Trezor may be invisible, pushing the user back into pairing
   mode — which changes the device identity and invalidates the bond. Resolving
   a known device by its stored identity address would avoid the loop.
4. **The device sleeps sooner over Bluetooth**, being on battery rather than bus
   power. THP has PING/PONG control bytes already implemented, so a keepalive is
   straightforward.
5. **Bluetooth scanning runs during ordinary device enumeration.** It is kept
   short, cached, and backs off after repeated empty scans, but the honest fix is
   to gate it behind an explicit user action.
6. **CodeEntry is the only pairing method implemented.** Production firmware
   gates `SkipPairing`, `QrCode` and `NFC` behind debug builds, so the others
   would be untestable.
7. **An unexplained crash** occurred once immediately after a successful
   transaction broadcast over USB. The broadcast completed and confirmed, so it
   is post-send teardown rather than signing. No logs were captured and it has
   not reproduced.

## 11. What is deliberately not in this pull request

`contrib/depends` in this fork has bugs that break the Linux build for anyone,
independent of Trezor: meson cross-files pass `CC` through as a single string so
meson looks for a binary literally named `gcc -m64`; Tor's `--enable-fatal-warnings`
turns a `SYS_SECCOMP` redefinition against glibc 2.39+ into a build failure; and
`appimage_runtime` invokes `make` with an unrecognised flag.

Fixes exist but are **held back for a separate, depends-only pull request**.
They are unrelated to this change and bundling them would make both harder to
review.
